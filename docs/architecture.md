# 架构与设计取舍

## 为什么保留“引擎 + 适配器 + 账本”

外部信号、交易所状态与本地数据库可能不同步。工程上的重点是明确事件身份、订单身份、成交归属和未知状态，而不是只把一条消息转换成一次 HTTP 请求。

公开版保留原型的核心处理代码，并将运行入口收束到一个独立的离线接入层。演示不连接外部信号源，也不实例化真实交易所适配器。

## 原型的异步处理

`TradingEngine` 中保留 WebSocket 接收循环与后台处理协程：接收侧记录消息并入队，处理侧执行解析与状态变更。重连使用退避等待；同一仓位的平仓使用锁避免并发重复执行。

这仍不是可靠消息基础设施。当前接收队列有容量上限，满队列时直接丢弃；原始消息文件不能自动变成安全的重放机制。后续改进需要确定事件顺序、幂等键、持久化确认点与重放边界。

## 演示接入层

`DemoSession` 拥有独立临时目录和 SQLite 数据库。启动时加载仓库中的合成 JSON 事件，按顺序交给演示引擎。

`DemoEngine` 在已有模拟分支外增加合成目录的交易所选择，并按原记录选择模拟平仓适配器。它不启动原型的网络接收、自动后入、真实账单同步或账户配置迁移流程。

`OfflineExchange` 注入固定价格与过滤器。模拟订单只加入进程内列表，不创建交易所 HTTP 客户端。重复回放共用同一账本，因此能够检查重复事件是否再次创建订单。

演示接入层的目录路由是对原型路由的可视化说明；原型实际路由分支另外用假交易所回归验证。两者不能混写成一次真实交易所端到端测试。

## 数量与金额

数量与账本计算使用 Decimal。合约过滤器决定数量步进、最小数量和最小名义价值。Gate 适配实现还需要处理合约面值与小数张数量，并保留小数数量响应头。

账本函数 `signal_net` 统一计算历史和统计的净值：普通记录按毛值减开仓费用、平仓费用和资金费；受限恢复记录只有在证据来源条件满足时才使用原始净值。

演示中所有费用均为模拟估算。网页前端把字符串转换成 Number 只用于显示和绘图；持久化和净值运算仍在 Python Decimal 层完成。

## 证据不足时保守失败

- 下单超时是“结果未知”，不等价于“下单失败”，不能无条件重试。
- 满页分页重复、成交号缺失或区间不完整时，拒绝用不完整结果覆盖已有账本。
- 部分平仓需要分摊已归属费用，不能在父记录和子记录里重复计费。
- 资金费归属不清时保留待核对，不按本地数量倒推外部账单。
- 新事件可以按配置路由，已有记录的加仓和平仓应回到原交易所。

## 隔离与资源清理

公开演示只注册展示和回放接口，不注册真实交易控制接口。入口绑定 `127.0.0.1`，并为专用 Python 进程安装回环网络审计限制。写请求会检查浏览器 Origin，拒绝外站触发回放。

FastAPI lifespan 创建和关闭会话；正常退出时关闭 SQLite 并清理临时目录。异常断电可能留下系统临时文件，重新启动不会复用这些目录。

公开扫描是规则检查，不能代替人工审阅、完整凭据扫描工具或代码安全审计。实际首次发布还需核对 Git 暂存文件清单。

## 后续拆分方向

优先把 `core.py` 中的精度与领域模型、SQLite 仓储、交易所适配器拆开，再把 `engine.py` 中的生命周期、账单同步和历史兼容迁移分离。在拆分前后使用相同合成输入比较订单序列、状态与原始金额精度，避免为结构美化改变资金口径。
