# 项目介绍与面试准备

## 一段可用的项目概述

项目名称：**基于 Python 的多交易所信号执行与账本管理系统**。

项目围绕外部信号的接收、交易所适配、状态管理和账本核对展开，使用 Python、FastAPI、asyncio、SQLite 与 Decimal。工程重点包括跨交易所路由、数量精度、重复事件处理、超时未知状态，以及手续费和资金费的归属。公开版提供固定行情、合成事件和临时数据库，便于无需真实账户地复现主要流程。

以上描述的是工程能力范围。简历中的“我负责”“独立完成”只能用于本人实际参与且能够解释、验证的部分；未完成的线上验证和性能指标不要写成成果。

## 推荐演示顺序

1. 运行 `python -m signal_ledger`，解释为什么公开演示不需要任何密钥。
2. 展示 2 个模拟持仓、4 条结束记录以及包含盈亏的净值曲线。
3. 再次回放，说明重复信号没有增加订单或净值。
4. 筛选 Bitget，解释优先路由与已有记录归属的区别。
5. 打开 `test_timeout_unknown`、`test_fee_window_fail_closed`、`test_partial_fee_allocation_preserved`，用测试解释异常处理。
6. 说明模拟与真实交易所验收的差别，再讲当前队列和大模块的改进方向。

## 应能回答的问题

| 问题 | 需要解释的关键点 |
| --- | --- |
| 为什么不用 float 算数量和费用？ | 十进制精度、合约步进、原始账单精度、最终展示舍入 |
| 重复收到结束事件会不会重复平仓？ | 记录状态、同仓锁、未知结果处理与幂等边界 |
| 为什么下单超时不能直接重试？ | 请求可能已到达交易所，传输失败不等于业务失败 |
| 为什么新单路由与旧仓管理要分开？ | 原订单与真实仓位归属不能随新配置切换 |
| 本地利润与交易所净值不同怎么办？ | 区分估算和实际账单，追查完整成交及费用归属 |
| 为什么分页不完整时保留旧账？ | 不完整证据不能覆盖已确认事实，也不能推进成功游标 |
| 公开版证明了什么？ | 合成场景、离线契约与状态处理；不证明策略盈利和外部接口可用性 |
| 下一步改进什么？ | 持久化队列、模块拆分、事件追踪、依赖与接口契约管理 |
